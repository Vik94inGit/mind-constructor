Backend field guide

Mind Constructor, endpoint by endpoint

Mind Constructor is a collaborative decision-mapping tool. A Map is one goal or discussion; a Node is one branch hanging off it — a Problem, an Option, a Solution, an outcome. This guide walks through every route the Express API exposes: what it does, who's allowed to call it, and exactly how the request travels from the client down to MongoDB.

Express 5 TypeScript Mongoose 9 / MongoDB Atlas JWT (jsonwebtoken) bcryptjs nanoid public ids

Who can do what

Six access levels repeat across every endpoint below. Once you recognize them, the whole API is really just these six rules applied to three resources.

LevelMeans
No authAnyone can call it — no token needed
Any signed-in userValid JWT required; no further check
Map memberYour user id must be in the map's members array (the owner is auto-added on creation)
Map ownerYour user id must equal the map's ownerId
Node creatorYour user id must equal the node's userId
AdminYour user document has role: "admin" — see Becoming an admin
The pattern to notice: the first five are almost never enforced with an if-statement and a 403. They're baked straight into the MongoDB filter — e.g. Map.findOneAndUpdate({ mapId, ownerId: userId }, ...) simply never matches a document you don't own, so the DAO returns null and the controller turns that into a 404. Fewer branches, and it's structurally impossible to forget the check in one code path but not another. Admin is the one deliberate exception — it's a real if (req.user.role !== "admin") in a dedicated requireAdmin middleware, because "admin" isn't a property of any document being queried, so there's no filter to hide the check inside.
Domain

Auth & users

Accounts, login, and two endpoints that manage the whole user table — useful for local development, dangerous anywhere else.

POST/api/auth/register No auth

Register

Creates a user. The password is never stored — only a bcrypt hash of it — and a JWT is issued immediately so the client is logged in the moment they sign up.

src/abl/authAbl.ts 
const registerSchema = z.object({
  username: z.string().min(1, "username is required"),
  email: z.string().min(1, "email is required").email("must be a valid email"),
  password: z.string().min(6, "Password must be at least 6 characters"),
});

export const registerAbl = async (input: unknown) => {
  const { username, email, password } = parseOrThrow(registerSchema, input);

  const existing = await findUserByEmailDao(email);
  if (existing) throw new EmailAlreadyInUseError();

  const user = await createUserDao({ username, email, password });
  const token = generateToken(user._id.toString());
  return { user, token };
};
400 error messages now come straight from the zod schema (e.g. "Password must be at least 6 characters") instead of a hand-written string in the controller — same wording as before for this one, but it's no longer duplicated logic if a second endpoint needs the same rule.
REQUEST BODY 
{
  "username": "alice",
  "email": "alice@test.com",
  "password": "secret123"
}
RESPONSE 201 
{
  "success": true,
  "token": "eyJhbGciOi...",
  "user": {
    "_id": "665f...",
    "username": "alice",
    "email": "alice@test.com"
  }
}

400 if any field is missing or the password is under 6 characters. 409 if the email is already taken.

POST/api/auth/login No auth

Login

Looks the user up by email, compares the submitted password against the stored bcrypt hash, and issues a fresh 7-day JWT on success.

REQUEST BODY 
{
  "email": "alice@test.com",
  "password": "secret123"
}
RESPONSE 200 
{
  "success": true,
  "token": "eyJhbGciOi...",
  "user": { "_id": "665f...", "username": "alice", "email": "alice@test.com" }
}
Every route marked map member, map owner, or node creator below relies on this token. protect (in src/middleware/auth.ts) reads the Authorization: Bearer <token> header, verifies it with jwt.verify, loads the user, and attaches it as req.user before your controller ever runs.
POST/api/auth/logout No auth

Logout

JWTs are stateless — the server never stores which tokens are "active", so it has nothing to revoke. This endpoint just returns a confirmation message; the actual logout is the client deleting its copy of the token.

POST /api/auth/logout→ logout()→ 200 "remove the token from your client"
GET/api/auth/users Any signed-in user

List all users

Returns every registered user, with passwordHash stripped by toPublicUser() before it leaves the controller.

GET /api/auth/users→ protect→ getAllUsers()→ getAllUsersDao()→ User.find({})
Deliberately not admin-gated — every other user needs this to find an id for Invite a member. Gating it would break invites, not tighten security. Everything below it, on the other hand, is admin-only.
DEL/api/auth/users Admin — wipes everything

Delete all users (and all their maps & nodes)

Empties the entire User, Map, and Node collections in one call. For resetting a dev/test database.

DELETE /api/auth/users→ protect→ requireAdmin→ deleteAll()→ deleteAllDao()
src/dao/userDao.ts 
export const deleteAllDao = async () => {
  const [users, maps, nodes] = await Promise.all([
    User.deleteMany({}),
    Map.deleteMany({}),
    Node.deleteMany({}),
  ]);
  return { users, maps, nodes };
};

403 { "error": "Admin access required" } for anyone without role: "admin". Still worth treating carefully even as an admin — it's irreversible and genuinely scoped to everything, not just your own data.

DEL/api/auth/users/{id} Admin

Delete a specific user

The most involved ABL orchestration in the app — deleting a user isn't one query, it's a sequence spanning three collections, which is exactly what doesn't belong stuffed into a controller or a single-purpose DAO function.

src/abl/userAbl.ts 
export const adminDeleteUserAbl = async (targetUserId, adminId) => {
  if (targetUserId === adminId) throw new CannotActOnSelfError(...);

  const user = await findUserByIdDao(targetUserId);
  if (!user) throw new UserNotFoundError();

  // Delete everything they own (deleteMapDao cascades to nodes already).
  const ownedMaps = await listMapsByOwnerDao(targetUserId);
  for (const map of ownedMaps) {
    await deleteMapDao(map.mapId, targetUserId);
  }

  // Unlink them from maps they were just a member of.
  await removeUserFromMapsDao(targetUserId);

  await deleteUserDao(targetUserId);
  return { deletedUserId: targetUserId, deletedOwnedMaps: ownedMaps.length };
};
What's deliberately left alone: nodes this user created on maps they don't own (i.e. maps where they were just a contributor) are left in place. Deleting someone's account shouldn't erase other people's shared discussion just because one contributor is gone — their userId reference on those nodes simply becomes dangling, and populate("userId", "username") resolves it to null from then on.
RESPONSE 200 
{ "success": true, "deletedUserId": "665e...", "deletedOwnedMaps": 2 }
RESPONSE 400 (deleting yourself) 
{ "success": false, "error": "You can't delete your own account" }
PATCH/api/auth/users/{id}/block Admin

Block a user

Sets isBlocked: true — a much gentler moderation tool than deleting: reversible, and it keeps all their data intact. This is the one place in the whole API where you can see the payoff of the JWT statelessness trade-off discussed earlier: blocking works instantly, on the next request, with no waiting for a token to expire.

src/middleware/auth.ts 
const user = await findUserByIdDao(decoded.id); // re-checked on every request

if (user.isBlocked) {
  return res.status(403).json({ success: false, error: "This account has been blocked" });
}

400 if you try to block yourself, 404 if the target doesn't exist.

PATCH/api/auth/users/{id}/unblock Admin

Unblock a user

Sets isBlocked: false. Same shape as Block, no self-check needed (unblocking yourself isn't a risk).

Becoming an admin: there's no in-app promotion endpoint — that would be a privilege-escalation hole waiting to happen. Instead:
npm run admin:promote -- someone@example.com
That runs scripts/promoteAdmin.ts locally against the same database the app uses, setting role: "admin" directly. No new login needed — protect reads role fresh from the database on every request, so an already-issued token becomes an admin token the moment the database record changes.
Domain

Maps

A Map is one goal or discussion board. It's mounted at bare /api (not /api/maps) — so "create a map" is POST /api/, and "get one map" is GET /api/<mapId>.

POST/api/ Any signed-in user

Create a map

The caller automatically becomes the owner and first member. A short public mapId is generated right here — that's the id every other Map/Node route uses from now on, never Mongo's own _id. ownerColor is mandatory: you can't create a map without also picking the color your contributions will show up as. An optional template seeds a starting node structure via createNodeAbl right after the map itself is created — see MAP_TEMPLATES below; omit it (or send "blank") for today's long-standing behavior of an empty canvas.

src/abl/mapAbl.ts 
const MAP_TEMPLATES = {
  blank: [],
  "single-problem": [{ text: "Problem", type: "Problem" }],
  "decision-tree": [{ text: "Problem", type: "Problem", children: [
    { text: "Option A", type: "Option" },
    { text: "Option B", type: "Option" },
  ]}],
  "pro-con": [{ text: "Topic", type: "unknown", children: [
    { text: "Solution", type: "Solution" },
    { text: "Problematic option", type: "Problematic option" },
  ]}],
};

const createMapSchema = z.object({
  name: z.string().min(1, "Name is required"),
  ownerColor: hexColor("ownerColor"),
  color: hexColor("color").optional(),
  template: z.enum(Object.keys(MAP_TEMPLATES)).optional(),
});

export const createMapAbl = async (input: unknown, ownerId: string) => {
  const { template, ...parsed } = parseOrThrow(createMapSchema, input);
  const map = await createMapDao({ ...parsed, ownerId });
  if (template && template !== "blank") {
    await seedTemplateNodes(MAP_TEMPLATES[template], null, map.mapId, ownerId);
  }
  return map;
};
REQUEST BODY 
{
  "name": "Discussion about AI",
  "color": "#4f46e5",
  "ownerColor": "#22c55e",
  "template": "decision-tree"
}
RESPONSE 201 
{
  "mapId": "aB3xQ9kLm2",
  "name": "Discussion about AI",
  "ownerId": "665e...",
  "members": ["665e..."],
  "memberColors": [{ "userId": "665e...", "color": "#22c55e" }],
  "color": "#4f46e5"
}

400 if name or ownerColor is missing, ownerColor isn't a valid hex color (#rgb or #rrggbb), or template isn't one of MAP_TEMPLATES' keys. Don't confuse ownerColor with the map's own color field above — that's the board's cosmetic color; ownerColor/memberColors is per-person, for telling contributors apart. The response is the map itself, same shape either way — any seeded template nodes only show up via GET /api/:mapId/nodes, same as if they'd been created one at a time right after.

GET/api/?filter=owned Any signed-in user

List my maps

Returns maps scoped to the caller. filter is an optional query-string parameter — "all" (owned + shared, the default), "owned", or "shared".

GET /api/?filter=owned→ getAllMaps()→ getMapsDao(userId, filter)
src/dao/mapsDao.ts 
switch (filterType) {
  case "owned":  return await Map.find({ ownerId: currentUserId });
  case "shared": return await Map.find({ members: currentUserId, ownerId: { $ne: currentUserId } });
  case "all":
  default:       return await Map.find({ $or: [{ members: currentUserId }] });
}
GET/api/{mapId} Map member

Get one map

One query does the lookup and the authorization check together — if you're not a member, the filter simply never matches.

src/dao/mapsDao.ts 
export const getMapByIdDao = async (publicMapId, userId) => {
  return await Map.findOne({
    mapId: publicMapId,
    $or: [{ members: userId }],
  }).exec();
};

404 Map not found either way — a non-member gets the same response as a truly nonexistent map, so the API never confirms a map's existence to someone who isn't part of it.

PATCH/api/{mapId} Map owner

Update a map

Send only the fields you're changing. Same pattern as above, but the filter checks ownerId instead of members — only the owner may rename/recolor/move the map, or flip discussionMode (see Combat) once it's already live, not just at creation.

REQUEST BODY (partial) 
{ "name": "Renamed board", "color": "#22c55e", "discussionMode": true }
RESPONSE 200 
{ "success": true, "map": { "mapId": "aB3xQ9kLm2", "name": "Renamed board", "discussionMode": true, ... } }
DEL/api/{mapId} Map owner

Delete a map

Owner-only, and cascades: every node on the map is deleted first, then the map itself.

src/dao/mapsDao.ts 
export const deleteMapDao = async (publicMapId, userId) => {
  const map = await Map.findOne({ mapId: publicMapId, $or: [{ ownerId: userId }] });
  if (!map) return null; // doesn't exist, or you're not the owner

  await Node.deleteMany({ mapId: map._id });
  return await Map.findByIdAndDelete(map._id);
};
POST/api/{mapId}/invite Map owner

Invite a member

Adds another user's id to the map's members array (via $addToSet, so inviting the same person twice is harmless). Only the owner can invite.

REQUEST BODY 
{ "userIdToInvite": "665abc..." }
RESPONSE 200 
{
  "success": true,
  "map": { "mapId": "aB3xQ9kLm2", "members": [ { "username": "alice" }, { "username": "bob" } ] }
}

userIdToInvite is the invitee's Mongo _id — get it from "List all users" or from your own frontend's user picker.

PATCH/api/{mapId}/color Map member

Set my color on this map

There's no "accept invite" step in this API — Invite a member adds someone to members immediately. So this is where the "when you're invited, pick your own color" part actually happens: any current member (the owner included) calls this themselves, whenever they like, to set or change their color. Two members can't hold the same color on one map at the same time.

Notice the split: whether a color is available is a business rule (does anyone else on this map already have it?) — that lives in mapAbl.ts. The DAO underneath doesn't know "taken" is a concept; it just pulls the old entry and pushes the new one when told to.

src/abl/mapAbl.ts 
export const setMapColorAbl = async (publicMapId, userId, input) => {
  const { color } = parseOrThrow(setColorSchema, input);

  const map = await getMapByIdDao(publicMapId, userId);
  if (!map) return null; // doesn't exist, or you're not a member

  const takenByOther = map.memberColors.some(
    (mc) => mc.userId.toString() !== userId.toString()
         && mc.color.toLowerCase() === color.toLowerCase(),
  );
  if (takenByOther) throw new ColorTakenError();

  return await setMemberColorMutationDao(map._id, userId, color);
};
src/dao/mapsDao.ts 
// Pure mutation — no decisions, just remove the old entry and add the new one.
export const setMemberColorMutationDao = async (mapInternalId, userId, color) => {
  await Map.updateOne({ _id: mapInternalId }, { $pull: { memberColors: { userId } } });
  await Map.updateOne({ _id: mapInternalId }, { $push: { memberColors: { userId, color } } });
  return await Map.findById(mapInternalId);
};
REQUEST BODY 
{ "color": "#f59e0b" }
RESPONSE 409 (color taken) 
{ "success": false, "error": "That color is already taken by another member of this map" }

400 if color is missing or not a valid hex color. 404 if the map doesn't exist or you're not a member.

GET/api/{mapId}/summary Map member

Get map summary

Returns the map plus its total node count.

GET /api/{mapId}/summary→ getMapSummary()→ getMapSummaryDao(mapId, userId)→ Map.findOne({mapId, members: userId}) + Node.countDocuments

GET/api/{mapId}/nodes Map member

List all nodes on a map

The real "give me the whole tree" endpoint — every node on the map, populated with each creator's username, visible to any member (not just the ones you personally created).

  return await Node.find({ mapId: map._id }).populate("userId", "username");

Domain

Nodes

A Node is one entry in the tree hanging off a Map — mandatorily classified by type (Problem, Problematic option, Option, Solution, Success, Fail, or unknown as a conscious "not categorized yet" choice), and linked to its parent node via parentId for the tree shape. Mounted at /api/nodes.

Nodes also carry combat state — health (starts at 100) and defeated — used by the Attack endpoints further down.

Reading and writing a node are checked completely differently — that split is the main thing worth internalizing about this domain:
POST/api/nodes/{mapId} Map member

Create a node

Only members of the target map may add to it. isFirstNode is computed by counting the map's existing nodes before this one is inserted — a convenience flag for the frontend to know it just created the root node.

The clearest case in the app for why ABL exists: creating a node is a membership check, a zod validation, a count, and an insert — four steps across two collections, coordinated around one decision (is this the first node?). None of that belongs jammed into the controller or bolted onto a single-purpose DAO function.
src/abl/nodeAbl.ts 
export const createNodeAbl = async (input, publicMapId, userId) => {
  const parsed = parseOrThrow(createNodeSchema, input);

  const map = await getMapByIdDao(publicMapId, userId);
  if (!map) throw new MapNotFoundError();

  const isFirstNode = (await countNodesByMapInternalIdDao(map._id)) === 0;

  return await createNodeMutationDao(map._id, { ...parsed, userId, isFirstNode });
};
REQUEST BODY 
{
  "text": "Ship v1 by Friday",
  "type": "Problem",
  "x": 100, "y": 200,
  "parentId": null
}
RESPONSE 201 
{
  "nodeId": "k4Tz1PqXaB",
  "text": "Ship v1 by Friday", "type": "Problem",
  "mapId": "665d...", "userId": "665e...",

type is mandatory — 400 if it's missing or isn't one of the seven values above. That's deliberate: it forces whoever's adding a node to actually decide what kind of claim it is, rather than leaving everything uncategorized by default. For a child node, pass an existing node's nodeId as parentId.

GET/api/nodes/{nodeId} Map member

Get one node

Fetches a single node — but the permission check isn't on the node itself, it's on the map the node belongs to.

src/dao/nodeDao.ts 
export const findNodeDao = async (publicNodeId, userId) => {
  const node = await findNodeByPublicIdDao(publicNodeId);
  if (!node) return null;

  const isMember = await isMapMemberDao(node.mapId, userId);
  if (!isMember) return null;

  return node;
};
PATCH/api/nodes/{nodeId} Node creator

Update a node

Narrower than reading: only whoever created this specific node can edit it — being a fellow map member isn't enough. Includes symbolOverride ("check" | "cross" | null) — manually forces the OutcomeBadge inner symbol regardless of type; null clears it back to the type's own default. Only meaningful on an outcome type (not "unknown"), but nothing stops setting it on any type — it simply won't be visible until the node's type would draw an OutcomeBadge at all.

src/dao/nodeDao.ts 
export const updateNodeDao = async (publicNodeId, userId, updates) => {
  return await Node.findOneAndUpdate(
    { nodeId: publicNodeId, userId }, // must be the creator
    { $set: updates },
    { new: true, runValidators: true },
  );
};

DEL/api/nodes/{nodeId} Node creator

Delete a node

Same ownership filter as update — only the creator can remove it. Deleting a node with children currently leaves those children in place with a parentId pointing at a node that no longer exists; the frontend should decide how to display that (e.g. re-parent to root).

Domain

Combat

A third access rule, on top of the two above: a map member can attack any other member's node with one of three weapons. Attacking depletes the target's health; hitting 0 flags it defeated — still visible, just marked as lost the fight, no more attacks land on it.

Map.discussionMode (toggle via PATCH /api/:mapId) inverts who an attack can land on, not whether attacking works at all: normal rules require the target be someone else's node; discussion mode requires the opposite — you can only attack your own node (self-critique instead of combat). See Attack a node's 400 responses below for both directions of that check.

WeaponDamageCooldown
nitpick10none — spammable
counterpoint255 minutes
fatalFlaw5030 minutes

Cooldowns are per attacker, per weapon — using fatalFlaw doesn't touch your nitpick cooldown. Every attack is logged to a separate Attack collection with a snapshot of the damage dealt, which is both the cooldown's source of truth and the attack-history endpoint below.

POST/api/nodes/{nodeId}/attack Map member

Attack a node

Can't target your own node, and can't attack one that's already defeated. Two things happen on a successful attack: the target's health drops (same as before), and a new weapon node is created, pointing at the target — a real, permanent Node document (isWeapon: true), not a visual-only or computed thing. It shows up in normal node listings and counts just like any node a person created.

Every landed attack spawns its own weapon node — attack the same target three times and you get three weapon nodes accumulating around it, not one upgrading. Which icon it gets is a direct 1:1 mapping from which combat weapon was used (nitpick→sword, counterpoint→axe, fatalFlaw→spear) — a different, simpler idea than Attack indicators' severity-based icon choice, and the two intentionally don't share code.
src/abl/attackAbl.ts

Domain

Edges & graph insights

A separate concept from parentId (the argument tree) and from combat: an Edge is an arbitrary directed link between any two nodes on the same map, tagged positive, negative, or neutral (the default). Two read-only endpoints compute insights from the edge graph — auto-detected clusters and "under heavy fire" indicators — entirely on the fly. Neither is a real collection: nothing about them is ever written to the database.

This is backend-only, by design. Rendering a cluster as a blob, choosing a dashed vs. solid border, drawing a jagged red line, picking a weapon icon on screen — all of that is a frontend's job. This API returns the data (which nodes form a cluster, which node is under fire and how badly) and stops there.
POST/api/edges/{mapId} Map member

Create an edge

Both fromNodeId and toNodeId are public node ids, and both nodes must actually belong to {mapId} — nothing about two valid-looking node ids alone guarantees that, so it's checked explicitly.

src/abl/edgeAbl.ts 
export const createEdgeAbl = async (input, publicMapId, userId) => {
  const { fromNodeId, toNodeId, sentiment } = parseOrThrow(createEdgeSchema, input);
  if (fromNodeId === toNodeId) throw new SelfLoopError();

  const map = await getMapByIdDao(publicMapId, userId); // membership check
  if (!map) throw new MapNotFoundError();

  const [fromNode, toNode] = await Promise.all([
    findNodeByPublicIdDao(fromNodeId),
    findNodeByPublicIdDao(toNodeId),
  ]);
  if (!fromNode || !toNode) throw new NodeNotFoundError();

  if (fromNode.mapId.toString() !== map._id.toString()
   || toNode.mapId.toString() !== map._id.toString()) {
    throw new CrossMapEdgeError();
  }

  return await createEdgeMutationDao({ mapId: map._id, fromNodeId: fromNode._id, toNodeId: toNode._id, sentiment, userId });
};
REQUEST BODY 
{ "fromNodeId": "k4Tz1PqXaB", "toNodeId": "9mWs2LdQoY", "sentiment": "negative" }
RESPONSE 201 
{
  "edgeId": "qP2xN8fRkT",
  "mapId": "665d...", "fromNodeId": "665f...", "toNodeId": "665g...",

sentiment is optional, defaulting to "neutral". 400 for a self-loop or a missing field, 404 if either node doesn't exist, 400 if a node belongs to a different map than {mapId}.

DEL/api/edges/{edgeId} Edge creator

Delete an edge

Same ownership pattern as nodes — only whoever created the edge can remove it. Nothing to validate here, so this skips ABL entirely: the controller calls deleteEdgeDao(edgeId, userId) directly.

GET/api/{mapId}/edges Map member

List a map's edges

All edges on the map, populated so fromNodeId/toNodeId come back as { nodeId, text, type } instead of raw Mongo ids — same idea as List all nodes on a map.

POST/api/{mapId}/circles/select Map member

Select a circle

A "circle" is a node with 2+ direct parentId-children — the parentId "star" a frontend draws as a halo/horns backdrop around a node and its branch children. Circles aren't persisted; they're recomputed fresh from every node's parentId on every call, the same way a map's other derived views are. Selecting one locks every member node (Node.locked = true) and unlocks every other node on the map, then remembers the choice — snapshotting membership at selection time — on the Map's selectedCircle, so it survives a reload and syncs to other collaborators. A frontend's layout/physics loop is expected to treat locked as "don't reposition me"; the intent is that exactly one circle stays put while every other one is free to drift, so it stands out.

RESPONSE 200

RESPONSE 404 (stale rootId) 
{ "success": false, "error": "Circle not found — the graph may have changed since it was computed" }

rootId is recomputed against, not trusted verbatim — if the graph changed since whatever list of circles the caller saw (a child was reparented, deleted, etc.) and that root no longer has 2+ children, this 404s instead of locking a stale membership. Broadcasts circle:selected to the map's socket room on success.

POST/api/{mapId}/circles/deselect Map member

Deselect the circle

Clears selectedCircle and unlocks every node on the map. Broadcasts circle:deselected to the map's socket room on success.

GET/api/{mapId}/attack-indicators?threshold=3 Map member

Attack indicators

Flags any node receiving at least threshold incoming negative edges, with a severity-based weapon suggestion — sword at the threshold, escalating to axe and then spear the further past it a node gets.

Not the same system as Attack a node. That's an explicit combat action a member takes (weapon, cooldown, health, defeat). This is a passive signal computed from the edge graph — the two share vocabulary because they're both about one node being "under fire," but attackIndicatorAbl.ts never imports from attackAbl.ts and vice versa. Don't confuse a node with a low health value with one that shows up here; they're unrelated.
src/abl/attackIndicatorAbl.ts 
export const pickWeaponIcon = (incomingCount: number, threshold: number): WeaponIcon => {
  if (incomingCount >= threshold + 4) return "spear";
  if (incomingCount >= threshold + 2) return "axe";
  return "sword";
};
RESPONSE 200 
{
  "success": true,
  "threshold": 3,
  "indicators": [
    { "nodeId": "9mWs2LdQoY", "incomingNegativeEdges": 5, "weapon": "axe" }
  ]
}
Spawn/despawn/duplicate-prevention, solved by not persisting anything. The spec this was built from worried about spawning duplicate indicators and cleaning up stale ones. Neither problem can occur here: an indicator is just one row in a freshly computed array on every call. Delete enough negative edges and the node simply isn't in the array next time — there's no "despawn" step, because there was never a persisted "spawn" to undo.

Boot sequence

What happens when npm run dev starts server.ts:

dotenv.config()→ check MONGO_URI→ mongoose.connect()→ app.listen(PORT)

If MONGO_URI is missing, the process logs the failure and exits immediately rather than starting a server with no database. There's also an unauthenticated GET /__debug that just echoes the configured port — a manual "is this actually my server" check, dev-only.
